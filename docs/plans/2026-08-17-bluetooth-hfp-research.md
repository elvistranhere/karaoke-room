# Bluetooth quality collapse: what is happening and what we can do

## 1. Why opening a mic kills Bluetooth audio

A Bluetooth headset speaks two different languages. A2DP is a one-way, high-bitrate music pipe (stereo, 44.1/48 kHz, AAC/SBC). HFP (hands-free profile) is the two-way phone-call pipe: mono, 16 kHz at best. A headset cannot run both at once, so the OS picks one for the whole link. The moment the OS opens that headset's microphone, the whole link flips to HFP and your music output degrades with it. That is a Bluetooth/OS constraint, not a browser bug ([Oboe BT TechNote, 2023-02-14](https://github.com/google/oboe/wiki/TechNote_BluetoothAudio)).

What decides which mic opens is the audio session the OS puts the app in, not just the deviceId we request. On iOS, Apple's rule: if a session enables both `allowBluetooth` (HFP) and `allowBluetoothA2DP`, "the system gives hands-free ports a higher priority for routing" ([Apple docs, checked 2026-08](https://developer.apple.com/documentation/avfaudio/avaudiosession/categoryoptions-swift.struct/allowbluetootha2dp)). WebKit sets exactly that combination whenever any page capture is live: PlayAndRecord with `AllowBluetooth | AllowBluetoothA2DP | AllowAirPlay | DefaultToSpeaker`, mode VideoChat ([AudioSessionIOS.mm, main branch, read 2026-08-17](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/audio/ios/AudioSessionIOS.mm)). So on iOS the HFP drop happens even if we ask for the built-in mic. On Android, Chromium only flips into communication mode (SCO) when an input stream opens with effects enabled ([audio_manager_android.cc](https://chromium.googlesource.com/chromium/src/+/main/media/audio/android/audio_manager_android.cc)), so mic choice actually matters there.

## 2. What the web can do today

**iOS Safari: nothing that saves A2DP.** Confirmed by WebKit source above plus field reports of output jumping to speaker on gUM ([2025-02-04](https://medium.com/@python-javascript-php-html-css/ios-safari-forces-audio-output-to-speakers-when-using-getusermedia-2615196be6fe)). A host app cannot override the WebView's session; WebKit bug 167788 open since Feb 2017, still NEW with comments through Feb 2025 ([bug 167788](https://bugs.webkit.org/show_bug.cgi?id=167788)). `navigator.audioSession` ships only `.type` since Safari 16.4 (2023-03-27); `.state` still absent in 2026 ([bug 283417, filed 2024-11-20](https://bugs.webkit.org/show_bug.cgi?id=283417)). `type` maps to AVAudioSession categories, and `play-and-record` forces VideoChat mode, that is, HFP ([DOMAudioSession.cpp](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/Modules/audiosession/DOMAudioSession.cpp)). It only works when the microphone permissions-policy is enabled on the document. `setSinkId` on iOS exists from 18.4 (2025-03-31) but iOS exposes only one virtual system speaker; Safari 26.0 (2025-09-15) added speaker-vs-receiver toggling and fixed the "only works the second time" bug ([Safari 26.0 notes](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)). You cannot pick a Bluetooth output from the page.

**Android Chrome: partially fixable.** Selecting the built-in mic usually keeps the headset on A2DP, the standard vendor workaround ([Gcore docs](https://docs.gcore.com/streaming/faq/real-time-video-issues/audio-quality-is-reduced-when-using-bluetooth-headsets-in-video-call-apps)). `setSinkId` is not supported on Android at all (checked 2026-08, [caniuse](https://caniuse.com/mdn-api_htmlmediaelement_setsinkid)), so output follows the system route.

## 3. Ranked plan

1. **Detect the Bluetooth route and warn.** After mic permission, read `enumerateDevices()` labels in `/Users/elvistranhere/Workspaces/karaoke-room/src/hooks/useAudioDevices.ts` for AirPods/Bluetooth/HFP markers, and show a one-line banner: "Bluetooth headsets drop to phone-call quality while your mic is on. Use wired or speaker for best sound." Half a day. Buys the most user-perceived value per hour, since this is currently silent breakage.
2. **Android: default the mic to built-in when a BT output is active.** In `/Users/elvistranhere/Workspaces/karaoke-room/src/hooks/livekit/capture.ts` (deviceId constraint at lines 48, 181, 348), prefer the built-in input instead of `inputs[0]` when the route looks Bluetooth. One day including on-device verification. Real quality win on Android, no effect on iOS.
3. **audioSession type switching, iOS only.** Set `playback` while listening and only `play-and-record` immediately before capture starts, back to `playback` after it stops (Apple guidance, [bug 218012 comment 37, 2023-03-02](https://bugs.webkit.org/show_bug.cgi?id=218012)). Half a day. Buys correct media-volume and A2DP restoration for listeners and after singing, not during singing. Do not set it while capture is live.
4. **Hide the output picker on mobile.** No `setSinkId` targets on Android, speaker/receiver only on iOS 26+. Two hours in the Sound Profile modal.
5. **Native Capacitor shell with native voice I/O.** iOS: `playAndRecord`, mode `.default`, options `[.allowBluetoothA2DP, .defaultToSpeaker]`, omitting HFP, plus preferred built-in mic. Only works if capture moves out of WKWebView into a plugin wrapping livekit/client-sdk-swift with `isAutomaticConfigurationEnabled = false` ([LiveKit audio docs](https://github.com/livekit/client-sdk-swift/blob/main/Docs/audio.md)); LiveKit's own defaults include `.allowBluetooth` and must be overridden. Android: LiveKit `MediaAudioType`. This is the only true fix. Estimate 2 to 4 weeks. Optional extra on iOS 26 non-EU: `.bluetoothHighQualityRecording` for AirPods Pro 2/4, though Apple flags added input latency ([Apple docs](https://developer.apple.com/documentation/avfaudio/avaudiosession/categoryoptions-swift.struct/bluetoothhighqualityrecording), WWDC25 session 251).

## 4. Do not attempt

Overriding AVAudioSession from the Capacitor host while capture stays in the WebView (ignored, bug 167788). Expecting `setSinkId` to select a Bluetooth output on either mobile platform. Using `navigator.audioSession` on Android (not implemented through Chrome 154, [caniuse](https://caniuse.com/mdn-api_navigator_audiosession)) or expecting `.state`. Setting `playback` while the mic is open; it pins a category that cannot record. Fighting Chromium's AudioManager from Java; it saves and restores state, so it is a race. Watch two external bets before committing to native: rdar://145294046 (WebKit dropping AllowBluetooth) and WebKit adopting BT high-quality recording.
