# Mobile stack decision: Capacitor, React Native, or both

Status: decision record. Written 2026-08-17 against the current `src/` tree and four research legs run the same day.

Companion reading: `docs/plans/2026-08-17-bluetooth-hfp-research.md` (why capture has to leave the WebView), `docs/design/AUDIO-ARCHITECTURE.md` (what is shareable and what is not), `docs/plans/2026-08-17-capacitor-status.md` (the scaffold that exists today), `docs/plans/2026-08-16-cross-platform-playbook.md` (the earlier verdict this record supersedes).

Every claim below carries the date it was checked. Where a claim is unverified I say so in the same sentence.

---

## 1. The question

Karaoke Now is a Next.js web app. Voice runs over LiveKit's JS SDK, music runs through one YouTube IFrame player per client with the singer as clock authority, and the decisions (Zod protocol, `syncMath`, `volumeModel`, `audioRoutes`, `atmosphere`) are already pure TypeScript under test.

One thing forces a native shell and it is not distribution. It is the Bluetooth quality collapse. The HFP research (section 3, item 5) names exactly one true fix: an audio session set to `playAndRecord` with `[.allowBluetoothA2DP, .defaultToSpeaker]` and `.allowBluetooth` deliberately omitted, plus `isAutomaticConfigurationEnabled = false` on the LiveKit side. Section 4 of the same document rules out reaching that from a Capacitor host while capture stays inside WKWebView, because WebKit ignores the host's session (bug 167788, open since 2017-02, comments through 2025-02). So the fix requires capture to leave the WebView on iOS. That single requirement is what makes this a stack decision rather than a packaging decision.

Three options are on the table.

**Option A: stay Capacitor, write a custom native audio plugin.** Keep the entire Next.js app in a WKWebView / Android WebView, move voice capture and playback out of the WebView into a plugin wrapping `livekit/client-sdk-swift` and `livekit/client-sdk-android`, bridge the result back to the page. This is the current scaffold's implied path.

**Option B: pivot to React Native + Expo.** Rewrite the UI in RN, run `@livekit/react-native` for voice, run the YouTube IFrame API inside `react-native-webview` for music, keep the pure core shared, keep the web app alive as a separate surface.

**Option C: hybrid.** Ship a Capacitor shell as mobile v1 now (the `server.url` shell already scaffolded) while building the RN app behind it, then cut over.

## 3. Recommendation

**Pivot to React Native + Expo (option B), staged behind a two-week kill gate. Freeze the Capacitor track at its current JS-only scaffold. Reject the hybrid as a plan.**

### Why

**The Capacitor option's central promise does not survive contact with the requirement.** Its argument is "keep the UI free, pay only for the audio plugin." But WebKit bug 167788 means the fix is unreachable unless capture leaves the WebView entirely, and once capture is native, the page can no longer see a `MediaStream`. That takes `voiceMixer.ts`, `useSingerAudio.ts`, `useAudioLevel.ts` and `useAutoSyncOffset.ts` with it: per-person gain, level metering and receiver stats all have to cross a bridge, and two of those run on a 75ms tick. The saving is much smaller than "keep the UI" makes it sound, and the price is a native LiveKit bridge with no prior art, owned by one person, forever.

**React Native buys the one thing we actually came for, and it is already shipped.** The A2DP-without-HFP session is a config object in a tier-1 SDK, dated 2026-07-23, not a plugin we write. Everything above the transport keeps working because it is literally the same `livekit-client`: connection ladder, `karaoke-voice` publish path, `RoomEvent` handlers, `getStats()`, per-person `setVolume`, and the SDK even ships native FFT level hooks.

**One detail the orchestrator must carry into the spike: the SDK's default is the bug.** `getDefaultAppleAudioConfigurationForAudioState` returns `playAndRecord` with `['allowBluetooth', 'mixWithOthers']` and mode `videoChat`, which is functionally the same HFP-forcing combination WebKit sets. `registerGlobals()` applies it unless you pass `autoConfigureAudioSession: false`. Out of the box, RN reproduces our bug. The pivot is only worth anything if we explicitly override.

**Delivery and store risk both point the same way and neither is decisive.** EAS removes the Xcode day and `server.url` is a review liability the vendor itself disclaims. But these move the answer by about a week; do not let them carry the decision.

**The hybrid is the trap.** It looks like risk reduction and is actually two shells, two sets of native product work (push, haptics, deep links, foreground service, offline screen), two review surfaces, and one owner. The Capacitor v1 it ships still has the Bluetooth collapse, which is the problem we started with, so it buys distribution we do not urgently need at the price of the attention the real fix requires.

### First two weeks

Everything in week 1 is throwaway-safe: it is a measurement rig, not a rewrite. Everything in week 2 is work we want under any outcome.

**Day 0, today, regardless of the decision.** Start Apple Developer Program enrollment ($99/yr). Typically 24 to 48 hours, but individual identity verification can run a week, and it is the only genuinely serialized dependency across all three options.

**Week 1: the kill gate. Two spikes, one physical iPhone, one physical Android.**

1. **Day 1: rig.** Expo SDK 57 dev build with `@livekit/react-native` 2.12.0, `@livekit/react-native-expo-plugin`, `@config-plugins/react-native-webrtc`, `react-native-webview`. `eas device:create`, `eas build -p ios --profile development`. Smoke-test the version gap first: the Expo plugin repo was last pushed 2026-03-17 against Expo 54 and we are on 57.
2. **Days 2 and 3: Spike R1, audio.** `registerGlobals({ autoConfigureAudioSession: false })` plus an explicit `IOSAudioSessionPolicy`: recording as `playAndRecord` with `['allowBluetoothA2DP', 'defaultToSpeaker', 'mixWithOthers']` and mode `default`, playout as `playback` with `['mixWithOthers']`. `mixWithOthers` on the recording leg is deliberate, or the WebView's music gets interrupted the moment singing starts. Connect to our real LiveKit room with AirPods paired and publish a mic track. Measure: does the link stay on A2DP through publish; which microphone actually opens (we cannot select it, so this has to be true by elimination); does music keep playing; and does issue #422 (iOS microphone publishes zero audio samples, open since 2026-06-14 with no maintainer comment) reproduce on Expo 57. Repeat the equivalent on Android with `AndroidAudioTypePresets.media`.
3. **Day 4: Spike R2, YouTube.** Bare `react-native-webview`, `{html, baseUrl: 'https://localhost/'}` with `playerVars.origin: 'https://localhost'`, a real karaoke video. Four measurements: no Error 153/101/150; `getAvailablePlaybackRates()` returns fractional rates; `setPlaybackRate(1.05)` reads back as 1.05 on the mobile embed (this is where I expect trouble, because a WebView gets YouTube's mobile player); and the round-trip latency of `getCurrentTime` against `DEAD_ZONE_S = 0.05` in `syncMath.ts`. Confirm `pointerEvents="none"` still plays and still swallows touch on both platforms.
4. **Day 5: write up and gate.** Pass, fail or fall through to section 5.

**Week 2, only if the gate passes.**

5. **Seam debts D1 through D9** from AUDIO-ARCHITECTURE, about 2.5 days. They pay off on web today and they are the pre-work for any driver. D2 (`resolveCaptureProfile`) gets more valuable under RN, not less, because RN's translation is genuinely different: `livekit/react-native-webrtc`'s `MediaTrackConstraints` has no `echoCancellation`, `noiseSuppression`, `autoGainControl`, `channelCount` or `sampleRate` at all, so the profile has to translate to `AudioDeviceModule` calls on iOS and to nothing on Android.
6. **Move `/api/livekit-token` and `/api/youtube-search` onto the PartyKit Worker**, with an origin allowlist and a rate limit. Not throwaway under any option: an RN app has no browser origin, and a bundled-`webDir` Capacitor app would be `capacitor://localhost`. Today the endpoint is only safe because the shell loads our Vercel origin.
7. **Split the repo into `packages/core` and `apps/web`**, with `apps/mobile` added empty. Core is the pure layer from AUDIO-ARCHITECTURE section 2: `syncMath`, `volumeModel`, `audioRoutes`, `shared/protocol`, the `voiceEffects` constant table, `composeAtmosphere`. Web keeps deploying from main throughout; nothing about this step slows the web app down.
8. **Vendor the YouTube bridge, and make the handle async on web first.** Write our own thin `react-native-webview` wrapper against `react-native-youtube-bridge`'s protocol (MIT, roughly a WebView, one HTML template and a command dispatcher) rather than depending on a one-author package. Do debt D12 at the same time. **The web half of this landed on 2026-08-17:** `YouTubePlayerHandle`'s getters return promises and every call site in `useVideoSync.ts`, `RoomView.tsx` and `VideoProgress.tsx` awaits them, one tick in flight at a time, and a torn-down loop issues no further commands. The timestamp wrapper is the port itself rather than a bridge detail: `getTime()` answers `{ seconds, readAt }` and the drift loop anchors the server clock to `readAt`, so the read latency lands as latency instead of as bias. The web adapter fills both fields in one statement; **a bridge driver owes a `readAt` sampled in the page next to `getCurrentTime`**, not on the far side of the round trip, or item K4 comes straight back. An async handle works unchanged on web, so this lands on main and gets exercised in production before the mobile app exists.
9. **Freeze Capacitor explicitly.** Do not install `@capacitor/ios` or `@capacitor/android`, do not run `cap add`, and do not write shell product code (push, haptics, deep links, foreground service) against it. Add a line to `docs/plans/2026-08-17-capacitor-status.md` pointing here.

The UI rewrite starts in week 3 and is the long pole: 8 to 14 weeks total to a shippable mobile app, one engineer, on the leg-1 estimate. That number should be re-cost after the room screen, not before.

## 4. What we lose, and the mitigation

| Loss | Why | Mitigation for v1 |
|---|---|---|
| **Voice effects on mobile** | `voiceEffects.ts` is pure Web Audio and RN has no Web Audio over a LiveKit track. `react-native-audio-api` (Software Mansion, 0.13.3, 427k downloads/month) implements the node types we need but has no `createMediaStreamSource` or `createMediaStreamDestination`, so it cannot see or feed a LiveKit track. Maintainer on issue #872, 2026-07-21: "our implementation won't be available for quite some time." `DynamicsCompressorNode` is also still roadmap, and the warm preset uses a compressor quad. | Mobile v1 ships with effect `none` and the effect picker hidden behind a client capability check, not a room flag (`RoomState.flags` is room-scoped and this is a local capture decision). Then implement the chain once as a `LocalAudioTrack.setProcessor` native module: `livekit-client` explicitly exempts RN from its `AudioContext` requirement, so the insertion point is supported. Do debt D10 first so the native side reads one `EFFECT_PRESETS` table instead of six builder functions. Budget 2 to 3 weeks of Swift and Kotlin DSP, and note it is owed identically on the Capacitor path. This is the honest cost centre of the whole pivot and it is stack-independent. |
| **The atmosphere layer** | Fifteen registered `@property` custom properties, `oklch`, `color-mix`, and a native 2s cross-fade. RN has none of these primitives. | `composeAtmosphere` and `srgbSafeChroma` are pure and move to `packages/core` unchanged, so the colour decisions survive. The mobile writer becomes a Reanimated shared value interpolating in oklch and emitting plain colour strings, with a lower-fidelity cross-fade in v1. Keep the token names identical so surfaces still consume the contract rather than the inputs. |
| **Mixer fidelity** | `voiceMixer.ts`'s `source -> personGain -> masterBus -> duck -> limiter -> output` graph has no RN equivalent. | `RemoteAudioTrack.setVolume(v)` branches on `isReactNative()` and applies native per-track gain (range 0 to 10), and `resolveGains` already composes master and duck into the per-person number, so ops 11 folds cleanly. The limiter has no equivalent; iOS offers engine-level `setAdvancedDuckingEnabled` and `setDuckingLevel(0-100)`. If clipping is audible, add a soft clip inside `volumeModel.ts` where it is testable. Spike item: confirm `setVolume` is zipper-free, since sliders push values continuously. |
| **Mic check (live loopback)** | No RN primitive. `react-native-audio-api` can do mic to speakers standalone, but two engines contending for one `AVAudioSession` is its own device-testing problem, and `micCheckIsolationPlan` assumes a single graph. | Mobile v1 ships without mic check. The pure parts (generation-token cancellation, the isolation rules, `micCheckTransition` from debt D14) stay in core so a later native implementation reads a spec. |
| **Android NC hot-swap** | `AudioDeviceModule` throws on Android, and audio constraints do not exist in `react-native-webrtc`, so port op 5 has no Android translation short of native work against `CustomAudioProcessingFactory`. | Android v1 uses LiveKit's default processing and no per-turn NC swap. `resolveCaptureProfile` still decides; the Android driver's translation is an explicit documented no-op, which is the propagation rule working as intended. iOS keeps the swap via `setVoiceProcessingBypassed`, which needs no engine restart. |
| **iOS input selection** | `setPreferredInput` does not exist anywhere in `livekit/react-native-webrtc` (code search, 0 hits, 2026-08-17). `AudioSession.getAudioOutputs()` on iOS returns only `['default', 'force_speaker']`. | With `allowBluetoothA2DP` set and `allowBluetooth` omitted, iOS should not offer the headset's HFP mic at all, so built-in wins by elimination. This is precisely what Spike R1 measures. `findBuiltInInputId` keeps its web and Android consumers. |
| **Stereo singing capture** | The `musicStereo` preset wants `channels: 2`. `forceStereo` sets `stereo=1` in the SDP but the native ADM is a mono voice-capture path. | Treat as unverified and probably false. `resolveCaptureProfile` downgrades to mono on mobile, and the downgrade is a decision recorded in the core, not an accident inside a driver. |
| **One UI codebase** | Web and mobile diverge permanently. This is the reference product's own shape (Discord's web client is a separate React app) but it is still the real price. | `packages/core` carries every decision, and AUDIO-ARCHITECTURE section 5's propagation rule stops being aspirational and becomes the thing that keeps the two surfaces honest. Accept feature skew, write it down per release, and keep web as the primary desktop surface. |
| **A three-month-old iOS audio stack** | The Apple audio device module was rewritten in 2.11.0 (2026-05-26) and the session config path in 2.12.0 (2026-07-23), with two months of betas and a 2.11.1 emergency bump for a deadlock. Issues #422, #436 and #437 are open, and #437 (Android background subscription stalls after a remote rejoin) sits directly on the singer-rotation path. | Pin exact versions, never a caret, and keep the week-1 spike rig as a regression harness to run before every SDK bump. Subscribe to #422 and #437. |

Not a loss, but not solved by the pivot either: the YouTube Required Minimum Functionality terms (page last updated 2026-04-28) forbid overlays in front of an embedded player and modifications not described by the API, which is what `VideoStage`'s transparent blocker plus `controls: 0` is. That is true on web today, it rides along identically on both stacks, and it deserves its own decision separate from this one.

## 5. Kill criteria

These reverse or halt the decision. Each names the discovery, not a feeling.

**Reverses the pivot (back to Capacitor, or to no native at all):**

- **K1. Spike R1 fails on the session fix.** With `autoConfigureAudioSession: false` and the A2DP-only policy, the link still flips to HFP when the mic publishes, or the headset's HFP mic still opens. This is the entire reason to pivot. If it fails, RN has no advantage left that is worth a UI rewrite, and the question becomes whether native is worth doing at all this year.
- **K2. Issue #422 reproduces on Expo 57 with a physical iPhone and no workaround is found in three days**, with no maintainer response. An iOS mic that publishes zero samples is the product. Reversal here is temporary: re-run the gate on the next 2.12.x.
- **K6. WebKit ships the fix.** If rdar://145294046 (WebKit dropping `AllowBluetooth`) lands, or `navigator.audioSession` grows enough surface to express A2DP-without-HFP, the HFP document's item 5 evaporates. The remaining native wins (push, background audio) are far cheaper than either option here, and the correct answer becomes a PWA plus a thin shell. Watch this monthly; it is named as a standing external bet in the HFP research section 4.

**Halts the pivot without choosing Capacitor:**

- **K3. `setPlaybackRate` is a no-op or unreadable on the mobile YouTube embed inside a WebView.** Rate nudging is the one tool the drift policy cannot lose: `rateSupported = false` drops `PERSIST_DRIFT_S` from 0.35 to 0.15 and makes seeks the only correction, which is audible mid-song. This fails identically under Capacitor, so it does not choose a stack. It forces a sync redesign, and that redesign outranks the stack question.
- **K4. `getCurrentTime` round-trip bias exceeds the dead zone.** If the measured bias is a large fraction of `DEAD_ZONE_S = 0.05` and the `readAt` the port already carries does not remove it, the singer's own read biases the whole room and the loop oscillates between `NUDGE_UP` and `NUDGE_DOWN`. Same reasoning as K3: it is a design problem, not a stack problem, and it must be solved before either shell is worth building.
- **K7. Schedule.** If the RN room screen has not reached feature parity within six weeks of the gate passing, stop and re-cost with real numbers instead of the 8-to-14-week estimate. Two half-built UIs and one owner is the failure mode this record exists to avoid.

**Does not reverse the decision on its own:**

- **K5. Error 153 persists in the RN WebView** with `{html, baseUrl}` and a matching `origin` on a real device. Then we need our own proxy HTML page served from `karaoke-room.vercel.app`, which is the same cost both stacks were already budgeting. It reverses nothing alone; combined with K3 it means the music path needs rethinking regardless of shell.
- **K8. A hard external deadline** (an event, a paying customer) demands a binary on a phone before the RN room screen exists. Only then, ship the `server.url` Capacitor shell to internal tracks only. TestFlight internal groups need no beta review, and the Play internal track is not gated by the 12-testers-for-14-days rule that blocks production for accounts created after 2023-11-13. Never send that binary to public review; `server.url` is what Capacitor's own docs disclaim and what App Review guideline 2.5.2 objects to.
